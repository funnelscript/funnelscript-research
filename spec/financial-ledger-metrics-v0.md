## H-LEDGER1 — Traceable delayed, liquid-vs-recognized accounting
A caller explicitly constructs one `MarketingLedger` with immutable `trial_id`, currency code (caller-verified ISO 4217, *two minor units only* in v0), liquid initial cash (signed `Decimal`), nonnegative integer horizon measured in **days**, explicit nonnegative integer minimum settlement delay, and an ordered finite journal. Events are `LedgerEntry(trial_id, tx_id, kind, day, amount, currency, source_tx_id=None)`; kinds: `sale`, `settlement`, `ad_spend`, `other_cost`, `writeoff`. Amounts are strictly positive, finite, exact two-decimal `Decimal` monetary values, not floats, strings or silent rounding. Entries must have unique nonempty ASCII IDs, exact trial/currency matches and nondecreasing nonnegative integer days; same-day order is the supplied journal order. No second event scheduler: entries are already ordered and a fold consumes the prefix through `horizon`. No event after the horizon affects the current snapshot. Unknown/missing references, over-settlement, over-writeoff, too-early settlement and duplicate IDs reject. A receivable must be created by a preceding sale before a settlement/writeoff, and cannot be overdrawn. No automatic scheduled payment is synthesized.

For each processed event prefix, `cash = initial_cash + settled_receipts - paid_ad_spend - paid_other_costs` and `receivables = sum(open_sale_balances) = recognized_sales - settlements - writeoffs`, with zero initial receivables. Only `settlement` increases cash; `sale` changes recognition/receivables but not cash. Paid costs are cash debits; `writeoff` reduces receivables and reduces profit through recognized credit loss but is not a cash debit. `profit = recognized_sales - paid_ad_spend - paid_other_costs - writeoffs`. This v0 reports a declared simplified accrual basis and DOES NOT model taxes, refunds, unpaid expense accruals, external fees, payment processing, discounts, borrowing or existing receivable balances. Caller may permit negative cash; no universal cash halt. Explicit `insolvency_threshold: Decimal` uses strict `cash < threshold` across the initial and every posted entry checkpoint.

The fixture is hand specified: initial 100.00 SAR; day 0 ad debit 20.00 and other cost debit 5.00; day 1 recognized sale 60.00; day 3 collection against that sale 30.00, minimum delay 2 days, horizon 3. Final cash 105.00, outstanding receivable 30.00, recognized gross revenue 60.00, paid ads 20.00, paid other 5.00, profit 35.00. At horizon 1, cash 75.00 and receivable 60.00. Illiquid receivables never fund a cash debit.

Falsifier: an unpaid sale increases liquid cash, over-settlement is accepted, or any amount fails the independently calculated cash and receivable reconciliation.

## H-METRIC1 — Explicit attributable per-trial metrics
`evaluate_trial(population_result, ledger_snapshot, *, converted_state, attribution_label, insolvency_threshold)` binds the same `trial_id`, a complete identity-partition snapshot and its explicit model-defined conversion state to financial records within the same declared horizon. It validates that partition sets are pairwise disjoint and their union equals initialized IDs, and that the converted-state label is declared. In the bounded reference fixture the sole eligible set is the initialized population and converted IDs are the designated converted-state members. This does not assert that a generic `terminal` label universally means conversion. Conversion = unique matching IDs / eligible IDs, using `Decimal` with caller-selected precision. CAC = paid advertising / distinct converted ID count; undefined for zero conversions. ROAS = recognized gross revenue / paid advertising; undefined for zero spend. Both undefined cases use `None`, never 0 or infinity. All ledger activity is explicitly declared attributable to the trial by a nonempty `attribution_label`. No automatic segment-level monetary allocation or marketing causal attribution is claimed. Trial result stores full ledger snapshot, cash-ruin predicate, currency, horizon, trial ID, attribution, conversion count/rate, CAC, ROAS and profit.

Falsifier: duplicate conversion event increases count, 0 denominator is reported as zero, or recognized revenue is mistakenly replaced by settled receipts in ROAS.

## H-RISK1 — Empirical risk convention
`evaluate_risk(trial_metrics, alpha)` requires nonempty complete distinct trials of the same currency, reporting horizon, attribution label and insolvency threshold, and exact decimal `0 < alpha < 1`. Loss convention: signed `L=-profit`, including negative values for gains (not positive-part clipped), and ordered ascending for the **empirical nearest-rank** `VaR_alpha` at `ceil(alpha*M)`. `CVaR_alpha` is the empirical quantile-integral over the upper `1-alpha` tail, including fractional weight of the boundary observation where necessary; never simply `mean(L >= VaR)`. Ruin probability is the fraction of trials whose cash checkpoint (including start) was strictly below the explicitly declared threshold. No claim of independent replications, statistically reliable risk forecast or external validation. Expected hand references: losses [0,0,10,30], alpha=0.75 => VaR 10, CVaR 30; losses [0,0,0,100] => VaR 0, CVaR 100; losses [0,10,20,30], alpha=0.625 => VaR 20, CVaR 80/3 (fractional boundary).

Falsifier: ties produce CVaR 25 for [0,0,0,100] at alpha .75, or trials of different horizon/currency are silently combined.

## Architecture and decisions
- Selected: opt-in marketing Python reference ledger/evaluator in `src/funnelscript/stdlib/marketing/`, no event scheduler or automatic economic constraint in World/legacy. Reuse the Phase 007A `PopulationResult` API only as a read-only identity/partition source. No compiler keywords or dependency changes. A hand-authored reference journal is explicit and not inferred from unrelated source economic state variables.
- Rejected: a universal compiler balance constraint (violates DEC-009); patching `TelemetryAggregator` to pretend exact sample CVaR (would silently redefine legacy metrics); implicit event-to-sale conversion inference from World source; a new simulation engine.
- No new Accepted ADR. Such a decision is required before integrating automatic transaction generation into World handlers, changing legacy metrics, supporting cross-agent shared financial accounts, credit/adjustment/tax semantics, or promising validated market forecasting.
- Numeric environment: decimal fixed two-place validation; no silent quantization. Division produces rational-decimal under explicit local arithmetic precision; expressions such as 20/3 are approximate as repeating decimals and must not be described as exact rational values. Source and ordered journal fingerprint, runtime/package versions and trial/population manifest are required for strict replay. This model has no economic parameter defaults besides the explicitly documented precision/closed-record contract.

**External market validity, statistical calibration, causal inference, and real-world prediction accuracy were not tested.**
